# Identity model

## Users

`UserRecord` is the kit's view of an account:

| Field | Meaning |
|---|---|
| `id` | UUID string — the `sub` claim of every token |
| `email` | login identity (case-folded by products' stores) |
| `password_hash` | bcrypt (≥12 rounds); `None` for password-less accounts (DIM owner, OIDC-only rows) |
| `full_name` | display name |
| `is_active` | `False` ⇒ 401 on every authenticated surface (checked in `authenticate_session`) |
| `is_admin` | enables the `/api/v1/admin` surface and admin guard-rail bypasses |
| `failed_login_attempts` / `locked_until` | lockout state (see [security.md](security.md)) |
| `token_version` (`ver`) | global revocation counter — bumping invalidates every token the user holds |
| `created_at` | audit/user-listing metadata |

Deleting a user cascades (sessions, profiles, owned rows) — case 9 of
`CONTRACT_CASES` asserts the cascade is complete.

## Session families

A sign-in is a **family**: one `auth_sessions` row linking the access
and refresh tokens of that sign-in.

- `issue_session(kit, user, auth_mode=…, label=…, client_label=…)`
  creates the row and returns `(access_token, refresh_token | None,
  csrf_token)`. `client_label` is the device hint (derived from
  `User-Agent`); the flow label (`login`, `register`, …) is stored when
  no device hint exists.
- The refresh token's `jti` is generated by the flow and stored **as a
  SHA-256 hash** — the token itself is never persisted.
- `expires_at` (rolling) and `absolute_expires_at` (the
  `refresh_absolute_days` cap) bound the family's lifetime.
- `revoked_at` marks logout / logout-all / forced revocation.

### Rotation and reuse detection

Every `/api/v1/auth/refresh` mints a new refresh token for the family
(compare-and-swap on the stored `jti` hash — concurrent refreshes cannot
double-rotate). Presenting the **old** (already-rotated) token is
replay: the family is revoked entirely and the user's `ver` is bumped,
which invalidates every outstanding access token too. This is the
single most important theft-detection property of the design.

## Profiles

Profiles (workspaces/tenants of user data) are owned per user (1:N,
UUID ids, `is_default`, `last_used_at`). The kit does not own profile
*scoping* — products bind `X-Profile-Id` per the guideline §15 — but it
provides `kit.ensure_profile(user_id)` (auto-provision the Default) and
the `ProfileStore` protocol (`ensure_default`, `count_for`) so the
auth surfaces can provision identity-adjacent rows at register/DIM
time.

## Instance access modes

`instance_settings.auth_mode` ∈ `open` | `authenticated`
(`nx_auth.instance.InstanceMode`):

| Property | Behavior |
|---|---|
| DB-authoritative | read from the store on every request (`read_state` / `effective_auth_mode`) |
| Init-only | the env seeds it **only on an empty table**; later env flips are ignored |
| Fail-closed | a missing or unknown value reads as `authenticated` |
| Server rule | `open` is illegal on a server entrypoint — first-boot seeding converts it to `authenticated` with a loud warning |
| Mode changes | only through `request_transition` (admin-gated, guard-railed) — never at launch time |

Token/instance coupling (no-bypass):

- `local-boot` tokens (DIM) are valid only while the instance is `open`.
- `demo` identities are valid only while `demo_mode=true`.
- Changing `auth_mode` to `authenticated` invalidates local-boot
  sessions immediately (checked per request, not per mint).

`InstanceState` carries `auth_mode` + `demo_mode`; helpers:
`effective_auth_mode`, `can_accept_local_boot`, `can_accept_demo`,
`parse_auth_mode` (returns `None` for unknown input — callers fail
closed).

## Demo mode

`demo_mode=true` (also init-only, DB-authoritative) admits the fixed
demo identity (`AuthConfig.demo_user_id`). `can_accept_demo` gates it;
products pair it with guarded seeders that refuse non-demo targets
(§13). The kit's job is only to make the demo principal impossible on a
non-demo instance (case 11).

## Tenants (optional)

`nx_auth.tenants` supports products with hard multi-tenancy (health's
Class S):

- `require_tenant(principal, row_tenant_id)` — 403 when the row belongs
  to another tenant;
- `RoleResolver` / `RoleChecker` — map the kit principal to
  product-side tenant roles.

Health adds claims via `mint_token(..., extra={"tenant_id": …, "scope": …})`;
`extra` may never override the standard claims (enforced — `TokenError`).
